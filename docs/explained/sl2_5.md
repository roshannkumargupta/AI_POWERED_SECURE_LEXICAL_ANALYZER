# SL2-5: Provider and agent safety boundary

## What changed

SecureLex now has a provider protocol with groq as the local default and an optional OpenAI-compatible HTTP provider. Structured outputs are bounded and validated, with one repair attempt; prompt content is redacted and marked as untrusted data. Remote requests require a consent record held by the server for the browser session, and the workbench displays provider, model, location and consent state.

The agent tool gateway wraps the existing in-memory agent tools. Its allowlist rejects shell, network, filesystem and policy operations, checks operation permissions and JSON schemas, and limits calls. AI explain requests first analyze the current source and select evidence from that result. Build-with-AI returns a draft, runs the deterministic analysis pipeline on the candidate, marks requirement behavior unverified, and never executes generated code. Agent activity records summaries only; no source or prompt is stored.

The reused Fix Agent can adapt a deterministic fix candidate into a structured `PatchProposal` containing the target finding, edits, diff, rationale, expected outcome, assumptions and known risks. The proposal remains a draft; applying it is a separate user-approved workflow.

## Limits

groq was unreachable during this phase's verification, and its configured model was absent. Live model explain/generate was therefore not exercised. Existing rule-based analysis and old `/api/llm/*` routes remain available. Independent verification and an independent verifier agent remain in SL2-6.

## Viva questions

1. **Why keep the deterministic analyzer when adding model agents?**  
   Deterministic analysis continues to work without a provider and supplies the evidence that agent explanations and generated candidates are checked against.

2. **How is remote source disclosure controlled?**  
   The UI uses a per-tab session identifier. An explicit checkbox writes a server-side consent record, and remote AI operations require both that record and the consent flag in the request.

3. **How does the tool gateway constrain agent actions?**  
   It matches tool names against an allowlist, checks each tool's operation permission, validates arguments against a JSON schema, and applies a call budget. Tools such as shell, network, filesystem and policy editing are absent.

4. **Can the generated program be considered correct because analysis passed?**  
   No. It is a draft and is statically analyzed, but it is never executed. Requirement behavior remains unverified until tests or an independent verification phase establish it.

5. **What happens when groq is unavailable?**  
   AI routes return an unavailable response with setup guidance such as starting groq and running `configure GROQ_API_KEY in .env`; deterministic analysis remains operational.
