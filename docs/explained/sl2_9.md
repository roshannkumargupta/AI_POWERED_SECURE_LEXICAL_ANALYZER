# SL2-9 Viva Notes

### 1. Why is the API bound to loopback by default?

The service processes source code and holds per-session state. Loopback limits access to the local machine. If an operator configures a non-loopback bind, requests require an environment-configured bearer token checked with a constant-time comparison. A firewall remains appropriate.

### 2. How are browser requests and session state protected?

The API validates Host and Origin, sets an opaque HttpOnly SameSite=Strict cookie with a 12-hour lifetime, and keys consent, patch state, agent-event queries and Safety Lab result access from that cookie. Separate HTTP clients receive different session identities; the security test checks consent isolation.

### 3. Does SecureLex execute submitted source or run user tests?

No. Python syntax checking uses `ast.parse`. Optional analyzers use fixed allowlisted command arrays and never use `shell=True`; in this environment they fail closed because no OS network sandbox is available. The Run/Test feature is unavailable without an OS-enforced sandbox.

### 4. What resource controls are present and what remains?

Requests with a declared body larger than 1 MiB are rejected before schema parsing, source schemas are capped, and separate process-local rate limits cover analysis, AI and Safety Lab. Tool subprocesses have wall-clock and output caps. Analysis worker isolation and memory caps are not implemented; Windows currently has timeout behavior only, a documented gap.

### 5. How should we interpret model and analyzer results?

Source, model output and tool output are untrusted. Provider prompts redact common credential patterns, outputs are schema-validated, patches pass the independent deterministic verifier, and tool execution is gated. Prompt framing is not a complete prompt-injection defense; provider/analyzer results are limited to the checks that actually ran.
