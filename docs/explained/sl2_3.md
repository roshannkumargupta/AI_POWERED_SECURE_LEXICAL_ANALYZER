# SL2-3: parsers, syntax diagnostics and AST workspace API

## Viva questions

1. **Why use Python `ast` and Tree-sitter together?** Python's standard AST gives definitive syntax errors and a compiler-shaped tree for valid code; Tree-sitter can still expose a partial tree when Python rejects broken input.
2. **Why do Tree-sitter byte offsets need conversion?** Tree-sitter reports UTF-8 byte boundaries, while the editor uses UTF-16 columns. The adapter maps through the original source so emoji do not shift the shown ranges.
3. **Does a parser success mean the program is semantically correct?** No. Syntax and semantic checks have separate status dimensions; semantic status is incomplete when analyzers are unavailable.
4. **How are optional analyzers kept safe?** They use fixed allowlisted argument arrays, temporary files, output caps and timeouts. Execution is disabled unless an OS-enforced network-isolated subprocess boundary is available; submitted programs are never run.
5. **How does the AST stay navigable for large files?** The initial response enforces node and depth limits and marks truncation. Child IDs can be expanded through the node endpoint, and the in-memory analysis cache is bounded.

## Status and evidence

Tree-sitter parser diagnostics are marked incomplete because its error recovery is not compiler proof; Python `ast` syntax errors are definitive. See `reports/sl2_3_evidence.md` for the exact API probe, current tool discovery, test output and transport/security limitations.
