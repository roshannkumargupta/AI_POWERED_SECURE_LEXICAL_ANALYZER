# SL2-4 — Security analyzer and quality observations

## What changed

The security stage now adapts the existing internal rules, taint findings and optional ML-adjusted pipeline findings into the v2 `SecurityFinding` shape. External Bandit, cppcheck, Semgrep, clang-tidy and ESLint results have bounded normalizers and carry native tool/rule provenance. Merging requires an exact source range plus a shared CWE or category; merged findings union CWE/provenance and retain the highest severity observed. `/api/analyze/security` returns severity, CWE and tool counts in `findings_summary`.

The security response includes the taint-path objects referenced by findings; paths remain explicitly incomplete when the engine cannot certify every propagation edge. The quality stage measures cyclomatic complexity, inclusive function line span, decision nesting depth and declared parameter count from the parser tree for functions it recognizes. Each result is marked `measured=true` and has the function range. These are source-structure measurements, not runtime or performance claims. Optional radon/lizard cross-checks are not run.

The internal rule catalogue is generated from all instantiated plugin rules. The guide explains metadata, evidence, fixtures and test requirements. Structured `fix_example` values are reused as safe patterns when present; absent patterns are identified explicitly.

## Security boundaries and limits

No submitted program is executed. External analyzers are run only through fixed profiles in the allowlisted runner and only when its host-level network-isolation requirement is met. This Windows environment reports that isolation as unavailable, so adapter execution is disabled. The recorded Bandit JSON and cppcheck XML fixtures validate normalization without those executables. Semgrep is restricted to a local `rules/semgrep/` directory; no directory currently exists in the repository, so the adapter returns unavailable and never requests registry rules.

The existing taint output is preserved as evidence steps with original ranges. Paths remain incomplete because the engine does not certify every propagation edge. `sanitizer_missing` evidence is not mislabeled as a sanitizer step. External mappings are deliberately limited to known metadata and a documented mapping table in the implementation; unmapped rules have no CWE.

The repository has broad vulnerable/safe fixture sets in each language, but this phase did not establish a verified one-to-one vulnerable/safe pair for every Part 7.2 family in every applicable language. Do not read the catalogue fixture references as proof of that coverage. Such gaps remain explicit for follow-up fixture work.

## Viva questions and answers

1. **Why retain the existing internal engine?** It already coordinates rules, taint and optional ML; the facade adds a versioned finding contract without replacing the working engines.
2. **When are findings merged?** Only at an exact same range and a shared CWE or category.
3. **Can an external tool run arbitrary submitted code?** No. Fixed static-analysis argument profiles operate on a temp source file; executable profiles are not part of the security adapters, and the runner fails closed without OS-enforced network isolation.
4. **Why are taint paths marked incomplete?** Existing steps have real evidence ranges, but the engine does not prove that it has captured every intermediate edge.
5. **What do quality observations establish?** They measure syntax-tree structure such as branch count and function span. They do not establish runtime performance or correctness.
