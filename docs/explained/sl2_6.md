# SL2-6: patch proposals and independent verification

## What changed

SL2-6 introduces a version-bound patch draft. The server hashes the source with SHA-256 and checks that both the hash and client version still match before verifying or applying edits. Ranges use the repository's one-based, UTF-16 coordinate convention. Invalid, overlapping, out-of-source and oversized changes are rejected. A generated diff must match the actual edits.

`POST /api/fixes/propose` creates a draft from an existing safe rule fix or requests a structured draft from the configured provider. Proposing never changes source. `POST /api/fixes/verify` applies edits only to a temporary in-memory string and reports before/after analysis. `POST /api/fixes/apply` requires explicit approval, repeats verification and stores an undo point. `POST /api/fixes/undo` restores that source and advances the version again so stale requests remain detectable.

The independent verifier is a separate module. It runs the established analyzer, parser, available semantic checks and quality measurements on both source versions. It computes resolved, remaining and introduced findings. Proposal rationale, expected outcome and agent success text are not inputs to the decision. User tests are listed as unavailable because the project has no execution sandbox for submitted code.

The old `/api/fix` and `/api/fix-all` paths remain for compatibility. They now require independent verification; fix-all tries at most three distinct safe candidates.

The four-language E2E script is present, but it could not reach a server in this environment.

External security adapters, project regression fixtures and behavior tests are not claimed as run by the new verifier. Do not interpret a partial outcome as proof that a patch is correct or safe.

## Viva questions

**Q1. Why carry both source hash and source version?**  
A version represents the client's edit sequence; a SHA-256 hash independently checks the exact text. Both must match to reject stale or altered proposals.

**Q2. Does proposing a fix modify the editor text?**  
No. Proposals contain edits and a rendered diff. Only the explicit apply endpoint returns a changed source, and it first reruns independent checks.

**Q3. How does the verifier avoid trusting the Fix Agent?**  
It accepts source, language and a proposal's edits, then reruns deterministic analysis. It does not read the proposal's rationale or expected-success claim.

**Q4. What does “Partially verified” mean?**  
The available deterministic checks found the target resolved and no disqualifying introduced finding, but one or more checks (such as a compiler or user test) were unavailable. It is not a proof of runtime correctness.

**Q5. Why is user code not run during verification?**  
There is no isolated execution sandbox. The current verifier uses static analysis only and reports project tests as unavailable rather than executing untrusted code.
